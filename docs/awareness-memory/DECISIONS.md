| ADR-028 | Accepted from board netlist evidence (2026-08-28) | Correct the quad-pump hardware map to **GP6/GP7/GP8/GP9** for relay channels 1-4 and **GP0/GP1/GP2/GP3** for the unavailable fuse inputs. Channels are numbered in output-connector order J2-J5; pot assignment is made by which terminal a pump is plugged into, not in firmware. Relays remain active-high. | `Controller_Board_mk2.kicad_pcb` routes GP6->R1->Q1->K4->J2, GP7->R4->Q4->K3->J3, GP8->R3->Q3->K2->J4, and GP9->R2->Q2->K1->J5, with the fuse dividers reaching GP0-GP3 through R5-R8. The same netlist marks GP10, GP11 and GP12 `unconnected`, so ADR-022's GP9-GP12 table drove floating pins on channels 2-4 and no relay could move. ADR-022 was never verified against hardware - its own session handoff records that no physical command was issued after the change. Q1-Q4 are low-side NPN switches, confirming active-high. Supersedes the GPIO mapping portion of ADR-022 and ADR-018. |
| ADR-029 | Accepted (2026-08-28) | Raise `water_plants` `timeout_seconds` from 20 s to 45 s in the action registry. | Commit `25e3fd2` raised the firmware's `DEFAULT_RUN_SECONDS` from 8 to 30, and the legacy path publishes `status/{pin} = 0` only after the cycle completes. A 20 s state-confirmation timeout therefore marked every successful 30 s watering run as timed out. 45 s matches the canonical `run_pump` timeout and still bounds the request well inside the firmware's 30 s hard ceiling plus dispatch latency. |

| ADR-030 | Accepted from on-board measurement (2026-09-01) | Stage the quad-pump network connect across main-loop iterations so no single `ensure_connected()` call can exceed the watchdog budget: poll the Wi-Fi association instead of blocking on it, leave the MQTT handshake as the only blocking step, lower `SOCKET_TIMEOUT_SECONDS` from 5 s to 3 s, and feed the watchdog inside the connect and publish paths. | Measured on the board: a Wi-Fi join takes ~4.0 s and a TCP connect to an unreachable LAN host blocks for the full socket timeout (5.003 s measured). The previous code performed both inside one `ensure_connected()` call while `main.py` fed the 8 s watchdog only once per loop iteration, so a boot with the broker unreachable spent ~9 s between feeds and reset mid-connect - before the failure was ever recorded as a backoff. Every reboot repeated it, giving a permanent reset loop for as long as the broker stayed down; the board was found reporting `reset_cause == WDT_RESET`. Connect + CONNACK is now bounded by 2 x 3 s, and the worst observed single call under reproduction is 3218 ms against the 8000 ms budget. The RP2040 watchdog maximum is ~8388 ms, so the budget cannot be raised to fit the network - the blocking work had to fit under it. |
| ADR-031 | Accepted (2026-09-01) | Give the quad-pump firmware an explicit liveness bound and a recovery escalation ladder: drop the session when nothing has been received for `MQTT_INACTIVITY_TIMEOUT_MS` (90 s, four missed pings), power-cycle the Wi-Fi interface after `RECONNECT_RADIO_RESET_ATTEMPTS` (5) consecutive failures, and let `main.py` reset the board after `RECONNECT_HARD_RESET_ATTEMPTS` (20) - but only while no pump is running or queued. | The firmware sent PINGREQ every 20 s and never checked that a PINGRESP came back, so a half-open TCP connection left it reporting `mqtt_connected: true` and publishing into a socket nobody was reading, with no path back. Separately, nothing escalated: `ensure_connected` retried forever at the 60 s cap without ever resetting the CYW43, while the main loop kept feeding the watchdog - so a wedged radio was hidden rather than recovered. Measurement confirmed the escalation is needed: over repeated cold starts one association stalled and never completed within 40 s, recovering only when `connect()` was re-issued. The hard reset is gated on no in-flight run because a reset would otherwise cost a watering command its acknowledgement path. |
| ADR-032 | Accepted from on-board measurement (2026-09-01) | Set `WIFI_JOIN_TIMEOUT_MS` to 8000 ms as a stall detector for the polled Wi-Fi association, rather than a patience setting. | Repeated cold starts measured interface bring-up at ~970 ms and successful association at ~4.1 s, but a stalled association did not recover on its own within 40 s and needed a fresh `connect()`. An initial 15 s value made every stalled boot cost 15 s before retrying, observed as a 19.5 s time-to-online; 8 s is roughly twice the observed join, and cut a clean boot to 4.1 s time-to-online. Waiting here costs no watchdog budget because the join no longer blocks the loop (ADR-030). |
